# M0～M5 文件與功能符合性稽核（2026-10-14）

本報告的初次稽核依使用者要求先列問題，當時不修正產品、操作腳本或既有教學，只新增本報告與 Git 忽略的本機驗證產物；未 commit／push。下方 F01～F08 和初次檢查結果保留當時事實；後續授權的修正狀態另見 [修正追蹤](#修正追蹤)。歷史驗收結果保留原意。

結論：M0～M5 的主要垂直流程均有實作及既有真實 kind 驗收證據；本輪發現以下操作問題、文件落差與驗證缺口，不能把「文件檢查通過」解讀為所有指引完全正確。

## 問題清單

### F01：M4／M5 重建 Hub 會把自訂租戶配額改回預設值

- **類別／優先順序：實際行為問題，優先處理。**
- 文件：[M4 配額管理與停止恢復](../stages/m4/README.md)、[M5 重啟與結束](../stages/m5/README.md)。M4 明確提供 bootstrap 修改 quota、再同步至 Hub 的操作。
- 實作：`stages/m4/scripts/control.sh:119`、`stages/m5/scripts/control.sh:126` 的 `hub-recreate` 都呼叫 `workers()`；後者重新對 team-a／team-b 執行 `bootstrap-worker --action tenant`，沒有帶原本自訂的 quota。
- `stages/m4/cmd/bootstrap-worker/main.go:39` 起的預設值為 CPU requests=1、memory requests=1Gi、CPU limits=3、memory limits=2Gi、pods=8；`stages/m4/bootstrap/provision.go:64`／`:90` 會更新既有 ResourceQuota。
- **本輪已用真實 envtest API server 重現**：先設定 requests.cpu=2，再呼叫與重新 bootstrap 相同的預設 provision，讀回變成 1。日誌：`artifacts/audit-20261014/quota-repro.log`。這是隔離 API server 的真實物件更新，不是完整 Hub-recreate kind E2E。
- 影響：只是想更新 Hub／Agent endpoint，也會縮小或放寬租戶配額；Hub 先前保存的 profile 可能仍是舊值。M5 同一路徑也會重寫 values 的 rollout=1。保留 DB／ledger 不等於保留所有 Worker 設定。
- 建議：把更新 endpoint 與首次安全資源 provision 分開；重建 Hub 應保留既有 quota。補上自訂 quota → hub-recreate → quota／profile 一致性的回歸驗證。

### F02：M4／M5 E2E 殘留清理指引缺少必要的資源名稱設定

- **類別：無法完整照做的恢復指引。**
- [M5 README](../stages/m5/README.md) 第 171 行要求以「原 state 的正式 down」清理 E2E 殘留；M4 也說明殘留同名 E2E 資源會阻止重跑，但沒有完整清理命令。
- E2E 在自己的子程序設定 `HF_M4_A/B/HUB/DEX` 或 `HF_M5_A/B/HUB/DEX`；這些變數不會回到使用者原終端。見兩階段 `scripts/e2e.sh:3`～`:4`。
- 一般 `run.sh down` 的預設名稱仍是 hugofleet-a／b 和教學 Hub／Dex。**只設定原 HF_M4_STATE／HF_M5_STATE 並不足以選到 E2E 資源。** 結果會漏清理，或因教學資源的 ownership 不符而拒絕；下一次 E2E 繼續遭到同名殘留阻擋。
- 正常 E2E trap 有保留上述變數，所以本項不否定先前自動 cleanup 的 PASS；問題是失敗後由新終端手動恢復的文件。
- 建議：提供含原 state、A、B、Hub、Dex 全部五個變數的完整命令，或由 state 中的受信任紀錄恢復名稱。不能藉刪除 ownership 檔繞過。

### F03：M3／M4 的獨立測試指引漏列生成工具／envtest 前置安裝

- **類別：新環境重現缺口。**
- 根文件的 `make tools` 只安裝 Go／kind／kubectl。
- [M3 README](../stages/m3/README.md) 第 334～336 行只先執行 `make proto-tools proto-check`，接著卻執行需要 controller-gen 的 `verify-generated`，以及需要 setup-envtest 和已下載 API server／etcd 的 race／integration。
- [M4 README](../stages/m4/README.md) 第 124～129 行直接執行 `proto-check`、`test-integration`，未先準備 Proto generators 或 envtest。
- 實作確認：`stages/m1/scripts/control.sh:42` 要求 controller-gen；`:55` 要求 setup-envtest，且 `use -i` 只取已安裝 assets；`stages/m3/scripts/proto.sh` 的 check 分支要求三個 Proto 工具。各課 up 只建置所需映像，不會補齊這些主機測試工具。
- 影響：已有前階段工具的開發機會通過，但直接從乾淨環境選 M3／M4 的讀者會失敗，與「不必先操作其他課」的說明不完整一致。
- 建議：在測試段落先列 `make operator-tools envtest proto-tools`；不需要把這些工具變成單純閱讀或 Demo 啟動的強制前置。

### F04：M2 對新 revision／ReplicaSet 的教學仍描述舊行為

- **類別：已確認的文件錯誤。**
- [M2 README](../stages/m2/README.md) 第 331 行仍寫「同配置的新 revision 可能沿用原 ReplicaSet」。[ADR 0005](adr/0005-m1-operator.md) 第 12 行也保留原決策，沒有標記被後續決策取代。
- 現行 `stages/m1/controller/workload.go:53` 把 revision 寫入 Pod template；[ADR 0012](adr/0012-current-revision-replicaset-evidence.md) 已明確要求每個新 revision 觸發獨立 rollout，相同 revision 重送才維持原 template。
- **本輪 `TestPodTemplateBindsAcceptedRevision` 及相關 envtest／Unit 通過。** 新實作與 M1 現行教學相符，問題在 M2 教學與 ADR 的銜接。
- 影響：讀者可能錯估純縮放／相同配置發版的 Pod 替換與 surge quota，也可能誤解舊失敗如何歸屬。
- 建議：更新現行 M2 說明；ADR 0005 保留歷史內容並補上被 ADR 0012 取代的註記，像 ADR 0002 已有的作法。

### F05：M4／M5 的跨日恢復指引未說明開發憑證有效期限

- **類別：生命週期操作文件缺漏。**
- [M3 教學](../stages/m3/README.md) 有明確寫 leaf 24 小時、CA 48 小時及到期後的新 state 練習方式；[M4](../stages/m4/README.md)／[M5](../stages/m5/README.md) 的停止恢復段落未提供同等說明。
- 兩階段沿用 `stages/m3/devcert/certs.go:47`／`:61` 的同一有效期；`stages/m4/cmd/bootstrap-hub/main.go:69` 只在 CA 檔不存在時生成，不會因重新 up 或 hub-recreate 延長到期時間。
- 影響：隔天以原 state 恢復時，新的 mTLS 握手可能因 leaf 過期失敗；重新 build 或重建 Hub 不會修好。這不代表正在使用的 TLS stream 一到期就一定斷線，而是重新連線時會遭驗證拒絕。
- 建議：在 M4／M5 加入期限、診斷與已驗證的重新練習流程；保留歷史 DB 的原地憑證輪替仍應標示未驗證。不要引導直接刪 certs 或舊 DB。

### F06：真實 OIDC 負向測試沒有納入正式 Make／CI 驗證入口

- **類別：自動化驗證缺口，不是認證功能已失敗。**
- `stages/m4/test/oidc/oidc_test.go`、`backchannel_test.go` 都使用 `oidcintegration` build tag，包含真實 state／nonce／binding／PKCE、短期 session、JWT 自然到期及 canonical backchannel 的檢查。
- `make m4-test`／`test-unit` 沒有此 tag；race 使用 integration；M4／M5 kind E2E 只編譯 e2e tag；[CI workflow](../.github/workflows/ci.yml) 也沒有執行 oidcintegration。
- 正式 E2E 有真實登入／登出及 CSRF／角色驗證，不能說它完全沒測 OIDC；但不包含上述全部真實負向案例。
- [M4 驗收紀錄](m4-validation.md) 保存手動執行的 PASS 與命令，M4 README 也有提到另行測試。本項不撤銷歷史結果，只指出「日常完整門檻」無法自動防止這些測項回歸。
- 建議：提供可獨立準備短 session Hub／Dex、執行與清理的正式 target，再決定是否納入 CI。15 分鐘自然到期測試可有獨立 job，不應偽裝被一般 Unit 覆蓋。

### F07：規格要求的心跳／重試可配置能力尚未提供部署入口

- **類別：規格與交付介面落差。**
- [規格](../HUGOFLEET_SPEC.md) 第 512 行要求心跳閾值可配置並測試；第 852 行要求心跳／重試／部署逾時可配置。
- 套件層有 `Client.Heartbeat` 和 `Transport.HeartbeatTimeout`，測試也可縮短。但實際 Agent CLI 固定 Heartbeat=5 秒（`stages/m3/cmd/agent/main.go:103`），Hub 預設 timeout=15 秒，入口沒有相應旗標；重連退避的 1～30 秒也固定在 `agent/client.go`。
- 部署 timeout 有旗標，不能把它當作心跳／重試也已可配置。ADR 0008 描述固定值，未明確說取消這項規格。
- 建議：確認要交付有上下限的設定入口，或正式收斂規格為本機固定 profile。這不否定固定設定下已通過的斷線／重連功能。

### F08：ADR 0011 的目前狀態仍停在「實作中，待完整驗收」

- **類別：低優先文件一致性。**
- [ADR 0011](adr/0011-observability-and-delivery.md) 第 3 行與根 README、M5 README 和最新 validation 的本機完成狀態不一致。
- 建議：補上本機完成日期／驗收連結，仍保留 Hosted CI 未執行，不改寫歷史 FAIL，也不把 T18 標為通過。
